## 0. 结论速览

1. **不存在"建筑平面图 JSON 标准"这一件事。** 2026 年的现实是三个互不兼容的家族各自演化：地图/导航侧（IMDF、IndoorGML 2.0 / IndoorJSON、CityJSON）、建筑工程侧（IFC 为规范、JSON 只作为交换视图，外加 bSDD / D4C / SAREF / Speckle）、房产交易侧（RESO Data Dictionary、stream.estate、Centris、Spark、MagicPlan）。三边都在用 JSON，但没有一边能把另一边覆盖。〔S1–S20〕
2. **研究界已经事实上收敛到 ResPlan 式的"polygon 字典 + 类型化图"。** 键是语义类别（bedroom/bathroom/wall/door…），值是 Shapely `Polygon`/`MultiPolygon`，缺失类别写 `MULTIPOLYGON EMPTY` 而不是删键；连通性另给一张 rooms-as-nodes、edges 分 `via_door / via_window / adjacency / direct` 的图。CC BY 4.0，可直接商用。〔S1 S2〕
3. **OGC 在 2025 年做了一件对 JSON 很关键的事：IndoorGML 2.0 Part 1 把"模型"和"编码"解耦**，Part 1 只做概念模型（encoding-agnostic），GML / SQL / JSON 的具体编码留给 Part 2。也就是说"IndoorGML 的 JSON 长什么样"在 2026-11 仍是**未定稿**；社区先行实现是 IndoorJSON + API-IndoorFeatures（写入时做 schema 校验、PostGIS + pgRouting）。〔S4 S5〕
4. **AEC 侧不要指望 JSON 替代 IFC。** 标准化重心已从"几何序列化"移到"属性字典"：IFC（ISO 16739-1）+ IDS 表达规则 + bSDD / EN ISO 23386 的 property URI。JSON 在这一侧的角色是**视图**：D4C 用 JSON-LD、SAREF4BLDG 用 NGSI-LD、Speckle 用 `@id/@type` 的对象流（core Apache-2.0，且支持 type evolution）、Autodesk ADX 做云端转换。〔S10–S14〕
5. **AI 侧正在反向离开自由 JSON。** SpatialLM 明确输出的是"逐行 code 式 layout"而不是自由 JSON，且要求门窗必须引用已存在的 wall id；FMLM 用 markup + 约束解码把"可解析率"做成 100%；HouseDiffusion++/GSDiff 用矢量参数。共识是：**语法可约束、引用可校验**比"字段好看"重要。〔S21 S22 S23〕
6. **中国的标准窗口正在打开，而且方向恰好是"把户型指标变成机器可读字段"。** GB 55038-2025《住宅项目规范》给出量化底线；中房协《住宅建筑信息模型设计交付标准》团标在 2026-11-19 公开征集参编（截止 2027-01-13），主编单位是房协人工智能应用分会 + 中海，公开表述是把"好房子"指标转成 BIM 可识别的属性字段；安徽（2026-09-16）与重庆（DBJ50/T-570-2026，2026-12-15 实施）已有地方 BIM 交付标准。〔S27 S28 S29〕
7. **建议：自定义一个受约束的中间层（`fishplan/v1`），对外挂三个投影（IMDF / IFC / GB55038+bSDD），不要直接对外声称兼容任何标准。** 理由是本目录《掩码到挤出》备忘的第 11.1 节已论证：几何表示层的取舍决定能力上限，而"中线 + 厚度 + 洞口宿主关系"是既有可编辑性、又能投影到 IMDF 与 IFC 的最小公倍数。〔S6 S10 S27〕
8. **形状层仍然是 GeoJSON / TopoJSON 的天下，而"建筑语义"层没有人给轻量答案。** 通用编码解决几何与属性同构（GeoJSON 是 RFC 7946 的稳定底座；TopoJSON 用共享 `arcs` + `transform` 量化解决相邻房间重复存边界的问题）；一旦需要楼层、房间词表、构件语义，就必须跳到 IMDF / IndoorGML / IFC 三个重量级体系。**到 2026 年仍不存在"为展厅或单一室内平面而生的轻量矢量标准"，这正是自定义 schema 的合法空间**——但自定义必须自带到 GeoJSON 与 IFC 的导出通道，否则会成为孤岛。〔S33 S34 S41 S40〕

## 2. 概念边界与五层错配

**先说为什么要 JSON 化**（2026-11-12 那轮已论证，本轮仍成立）：传统平面是位图（PNG/JPG）或 CAD 二进制（DWG/DXF），缺点是不可编程、不可交互、语义丢失。JSON 的价值在于几何与属性同构、天然适配 Web/JS 生态、可被 GIS/BIM/可视化库直接消费、易做增量传输与版本 diff，并能把非空间属性（房间名、面积、展项、POI、状态）挂在几何上。核心矛盾始终是**几何表达 vs 语义/拓扑表达**——越靠语义与拓扑，越省空间、越利于导航与分析，但越需要约定词表。〔S33 S34 S41〕

把"户型 JSON"当一个东西，是这一轮调研里最容易犯的错。实际上有五层，每层的标准与买家不同：

| 层 | 关心什么 | 典型字段 | 谁定标准 | 常见误用 | 来源 |
|---|---|---|---|---|---|
| L1 几何 | 墙/洞/房间在哪里、多厚 | polyline / polygon / thickness | 无统一标准（各家自定） | 把 GeoJSON 当成"平面标准"，GeoJSON 里没有厚度与构件 | S6 S8 |
| L2 拓扑 | 房间如何连通 | nodes / typed edges | IndoorGML 核心贡献正是 Dual Space 与连通图 | 只给多边形不给图，导航/具身训练不能用 | S4 S1 |
| L3 语义 | 这是卧室还是展厅 | roomType 枚举 | RESO DD / bSDD / 各 MLS 自己一套 | 枚举不可映射，跨源合并要做人工字典 | S9 S15 |
| L4 属性/规范 | 面积怎么算、层高多少、合规吗 | 数值 + 单位 + 定义 | GB 55038、EN ISO 23386/bSDD、地方交付标准 | 面积口径不写清（中线/内净/套内/建筑面积），报价直接错 | S27 S9 S29 |
| L5 交换/交付 | 能不能被 Revit / Blender / 小程序吃 | IFC / DXF / GLB / IMDF ZIP / Speckle | buildingSMART、OGC、厂商 | 把交付格式当数据结构，编辑器无法回写 | S10 S6 S13 |

我们的痛点集中在 **L1+L2 无标准**、**L4 在中国正在被标准化**。这决定了策略：几何与拓扑自定义（可控），属性字典挂靠（bSDD / GB55038），交付格式做投影。

按可实施的方案族，全景共六大类（自 2026-11-12 调研并入，本轮补齐了市场侧两格）：

1. **通用地理空间编码**：GeoJSON（RFC 7946）、TopoJSON —— 见 §3.8；
2. **室内/建筑专用标准**：IMDF、IndoorGML 2.0 / IndoorJSON、CityGML / CityJSON —— 见 §3.2–§3.4；
3. **BIM / IFC 生态的 JSON 化**：IFC4.x、ifcJSON、IFC5/IFCX、web-ifc、xBIM、xeokit —— 见 §3.10；
4. **平台/厂商专有**：Autodesk APS（Model Derivative / View & Data）、Autodesk ADX、Speckle —— 见 §3.11、§3.5；
5. **Web 可视化管线**：SVG + D3.js、deck.gl / MapLibre / Mapbox GL —— 见 §3.9；
6. **学术数据集与自定义 schema**：ResPlan、ModRes、MSD、CubiCasa5K、FloorPlanCAD，以及项目自有的 HallLayoutSpec / `fishplan/v1` —— 见 §3.1、§5.2、§6.1。

## 3. 技术详解

### 3.1 ResPlan 事实上是研究界的 schema

ResPlan 的每条记录是一个 JSON-serializable dict，键为语义类别，值为 `Polygon` / `MultiPolygon`。三条设计值得直接抄：〔S1〕

1. **缺失类别写空几何而不是删键**（`MULTIPOLYGON EMPTY`），下游一条代码路径通吃，不需要 `if "balcony" in plan`。
2. **稳定的多边形顺序 → 图的顶点索引**，因此 room polygon 与 graph node 一一对应，不需要额外 id 表。
3. **墙不是线而是干净多边形**，厚度一致，可以直接挤出成 watertight 体量——这正是《掩码到挤出》备忘里"模式 A"能成立的前提。〔S1〕

图侧给的是 rooms-as-nodes + 类型化边（门 / 窗 / 相邻 / 直通），可直接喂 GNN、约束求解器或符号规划器。面积不是标注字段，而是**从几何算出**；真实尺度靠房源列表的 GFA 对齐，墙厚中位数约 21 cm。〔S1 S2〕

对立面也清楚：RPLAN 是 256×256 栅格、同类房间同层重叠；MSD 每条是"整层多单元"，要自拆单元并补共壁与入户门。跨数据集迁移会崩（ResPlan→MSD 的指标明显下滑），说明**"平面 JSON"不是可平移的表示，训练与评估必须同域**。〔S1 S31〕

### 3.2 IMDF GeoJSON ZIP 的工程化取舍

IMDF 是一个 ZIP 里的若干 GeoJSON：`building.json`、`footprint.json`、`unit.json`、`level.json`、`section.json`、`fixture.json`、`place.json`、`connector.json`。它的设计取舍非常明确：**为"楼层切片 + 室内导航"服务，不为构件建模服务**。〔S6〕

三点必须澄清的口径（早期资料与我们自己 2026-11-12 那份都有出入）：IMDF 由 **Apple 与 Mapbox 等推动**、后被 OGC 收为 Community Standard（编号 20-094），微软不是制定方而是**消费方**（Places / Indoor Maps）；`level` 带 `ordinal` 正是为了解决多楼层"上下叠放"；网上常见的 `Venue` / `Opening` / `Amenity` 是宽松叫法，**现行 1.9 对象表里没有这三个名字**——门与垂直交通走 `connector`，设施与目的地走带 `category` 的 `place`，词表另配 `categories.json` / `place_types.json` / `styles.json`。〔S6 S7 S41〕

关键的结构性短板：**IMDF 不是显式的图标准**，连通性靠 `connector` 隐含，路径网络不是一等公民，也不含实时定位——这正是它与 IndoorGML 的分工线（见 §3.3）。〔S41〕

值得借鉴的两点：`section` 用来表达"在某个高度上的切面"（把不同楼层在竖直方向错开，便于 2.5D 渲染）；`level` 与 `unit` 分离，房间是 unit、楼层是 level，二者用关系连。〔S6〕

要警惕的两点：几何是 GeoJSON，没有"墙厚/构件"概念，做 BIM 交付必须补一层；工程实践里最常见的失败是**属性字段被导出器丢掉**——微软 Places 的 Figma→IMDF 工作流文档专门强调要在导出时勾选 `Include id attribute`，否则 unit/level 关联全断。〔S7〕

### 3.3 IndoorGML 2.0 与 IndoorJSON

OGC 在 2025 年发布的 IndoorGML 2.0 Part 1 的最大变化是**模型与编码分离**：Part 1 只定义概念模型（单元、楼层、空间单元、门户、Dual Space 连通图），Part 2 才给 GML / SQL / JSON 的具体编码。这意味着"IndoorGML 的 JSON Schema"在 2026-11 还没有正式文本，任何自称"IndoorGML 2.0 JSON"的实现都是社区版。〔S4〕

社区版就是 IndoorJSON 与配套的 API-IndoorFeatures（pygeoapi 扩展 + PostGIS + pgRouting）：写入时做 schema 校验、支持逐层渲染与路径求解。这是目前最接近"标准化 JSON 室内模型"的可运行栈，但它解决的是**导航与拓扑**，不是构件。〔S5〕

对我们的判断：IndoorGML 2.0 的 Dual Space（ primal/双空间：空间单元为节点、门户为边，另加状态图）值得吸收进 L2 拓扑层，但**不要为了"挂靠 OGC"去把数据塞进一个尚未定稿的编码**。〔S4 S5〕

### 3.4 CityJSON 与 bSDD 属性字典才是重点

CityJSON 1.1 的两个工程智慧：一是 `transform`（translate + scale 的整数量化）让 JSON 里的坐标既短又无损，直接解决"GeoJSON 写浮点导致体积爆炸与精度不一致"；二是 `cityobjects` 的 `parents/children` + `type` + `semantic` + `appearance` 分层，允许 LOD1 体量与 LOD4 室内共存于一个文件。〔S8〕

bSDD（buildingSMART Data Dictionary）与 EN ISO 23386 提供的不是几何，而是**属性的唯一 URI + 数据类型 + 单位 + 所属分类**。这恰恰是"户型 JSON"最缺的东西：面积、层高、开间、净高、隔声等级这些字段，如果没有可引用的定义，跨机构交付就会变成各说各话。欧盟侧的趋势是"几何用 IFC/CityJSON，属性用 bSDD URI"。〔S9〕

结论：我们的 JSON 里每一个数值字段都应当带一个"定义来源"槽位（`"definition": "bSDD:<uri>"` 或 `"definition": "GB55038:4.2.3"`），而不是把单位写死在键名里。

### 3.5 AEC 侧为什么 IFC 仍是规范而 JSON 只是视图

IFC（ISO 16739-1）在 2026 年仍是建筑信息交换的规范层，主干编码是 STEP；IDS（Information Delivery Specification）负责"交付必须满足什么表达规则"。JSON 在这一侧的四种存在方式：〔S10〕

| 方式 | 代表 | 本质 | 对我们的可用性 |
|---|---|---|---|
| 属性字典 | bSDD / EN ISO 23386 | 定义字段含义 | 高——可直接引用 URI |
| 语义图/数字孪生 | D4C（JSON-LD）、SAREF4BLDG + NGSI-LD `BuildingSpace` | 把构件与观测放上图 | 中——运维/能耗场景 |
| 对象流平台 | Speckle（`id` + `speckle_type`，声明兼容 JSON Schema，支持 type evolution） | 版本化 + 多软件往返 | **高——最适合做我们的"交付投影"层** |
| 厂商云 | Autodesk Data Exchange | 封闭管道 | 低——绑定 Revit 生态 |

Speckle 值得单独说一句，但**字段名要先纠正**：现行序列化对象的三件套是 `id`（内容哈希）、`speckle_type`（如 `Base`、`Objects.Geometry.Mesh`、`Building.Room` 或应用自定义类型）、`applicationId`（来自 Revit/Rhino 的原始 id），再加属性与嵌套几何基元（Point/Line/Polycurve/Mesh），并支持分层与 detached 分块存储；早期 .NET 序列化里出现过的 `@type` 只是类型判别字段的旧写法。它的好处是"自定义 JSON 类型 + 服务端去重与版本"，core 为 Apache-2.0，`speckle_type` 字符串演进（type evolution）解决了"schema 改了老数据怎么办"——这正是 `fishplan/v1` 版本号策略该抄的做法。代价也要看清：它是**平台化方案（需服务器/工作区）**，不是"打开即用"的平面图文件标准。〔S13 S35〕

SAREF4BLDG 的 `BuildingSpace` + NGSI-LD 则给出了另一条便宜的路：如果平面要接 IoT/能耗，房间实体用 NGSI-LD 表达比自造字段更省事。〔S12〕

### 3.6 AI 侧反向选择 markup 与 code

有意思的是，生成侧正在**离开**自由 JSON：

- SpatialLM 的论文描述里，输出不是自由 JSON，而是"逐行 code 式 layout"，并且要求 door/window 必须引用已经存在的 wall id——把"引用完整性"写进语法，避免模型生成出悬空洞口。〔S21〕
- FMLM 用 Floorplan Markup Language + 约束解码，把"可解析率"变成硬保证（约束解码 = 100% 语法合法）。〔S22〕
- HouseMind 走层次化 VQ-VAE token，平面被离散成 token 序列，JSON 只在 I/O 边界出现。〔S22〕
- ResPlan 的图表示则是"给模型看结构"而不是"给模型写 JSON"。〔S1〕

**给工程侧的启示**：让 LLM 直接产 JSON 时，必须同时具备三件事——(a) 受限语法或 JSON Schema；(b) 生成时约束解码（或正则/语法采样）；(c) 生成后的拓扑校验（洞口是否落在宿主墙内、房间是否闭合）。缺任何一件，字段越少越"干净"的 JSON 反而越容易悄悄产出不可用几何。这与《掩码到挤出》备忘第 11.1 节缺陷 5（"尺度不能自证，不报错只是悄悄全错"）是同一类失效模式。〔S21 S22〕

### 3.7 三条硬约定

跨源比对后，所有"能跑通"的平面 JSON 都偷偷写死了三件事，我们必须显式声明：〔S1 S6 S8 S21〕

1. **朝向与坐标系**：z-up 还是 y-up（glTF 是 y-up，Blender 导出需 `+y up`），角度还是弧度，是否假设 Manhattan（正交墙）。ResPlan 明确是 plan-view 平面坐标 + 统一墙厚；IMDF 走 WGS84 + 楼层偏移。
2. **尺度锚点**：毫米/米必须由字段声明，且强制携带至少一个锚点（已知墙长或比例尺）。CityJSON 的 `transform` 是"整数 + 缩放"的范例，避免浮点歧义。
3. **共壁与洞口宿主**：墙必须是**中线 + 厚度**（否则两侧房间各出一块墙，厚度翻倍、Z-fighting），洞口必须是 `host_wall + t_along` 引用（否则改墙忘改洞）。IFC 用 `IfcOpeningElement` 表达宿主关系，ResPlan 用 polygon 布尔，Speckle 用 `id`/`applicationId` 引用——三家殊途同归。〔S1 S10 S13〕

### 3.8 几何底座 GeoJSON 与 TopoJSON

这两者不是"平面标准"，而是所有平面标准的**承载层**，值得单列。

**GeoJSON（RFC 7946）** 由 IETF 发布，基本单元是 `geometry`（Point / LineString / Polygon / MultiPolygon / …）→ 包进 `Feature`（可带 `properties`）→ 汇成 `FeatureCollection`。用于室内时的行业惯例是"房间 = Polygon、门 = Point、走廊中线 = LineString"，名称/类别/面积塞进 `properties`。优点是开放、极稳定、几乎所有 GIS 与 Web 地图库原生支持；缺点是**没有内建楼层概念、没有建筑词表、没有拓扑**——相邻房间会各自重复存一遍边界。〔S33 S41〕

**TopoJSON** 是 D3 生态的事实标准而非官方标准，核心是拓扑：几何由共享的 `arcs` 拼接，`objects` 引用弧线索引，配合 `transform`（scale/translate）量化坐标。结果是体积显著小于 GeoJSON，且**天然保证相邻区域无缝、无重叠缝隙**。两个必须知道的限制：这里的"弧"只是 `[x,y]` 点序列，**不支持 SVG 弧与贝塞尔曲线**，曲线靠密集采样近似；编辑与生成工具链远不如 GeoJSON 普及。〔S34〕

值得注意的是 `transform` 量化这个手法在 TopoJSON、CityJSON（§3.4）两处独立出现——**"整数顶点表 + 缩放/平移"是 JSON 几何压缩的通用答案**，我们的 `fishplan/v1` 若要压体积，应照抄而不是自创。〔S8 S34〕

定位：**GeoJSON 是导出通道**（让平面图能被 GIS / deck.gl 直接消费），**TopoJSON 是前端渲染优化**（分区悬停与共享边），二者都**不能当真值层**——因为都装不下墙厚与构件语义。〔S40〕

### 3.9 Web 可视化管线

展厅这类"区域 + 悬停 + 动线"的交互平面图，最便宜的链路仍然是设计器手绘而非建模：

```text
Inkscape 手绘 SVG → 取路径 d（绝对坐标）→ SVGOMG 压缩 / SvgPathEditor 整形
→ path → polygon → 组装 TopoJSON（type/objects/arcs）
→ topojson.feature() 转 GeoJSON → d3.geoPath 生成 SVG 路径 → CSS :hover 交互
```

优点是完全可控、前端友好、零后端；缺点是前期数据录入很重，且 SVG 规模变大后性能吃紧（DOM 节点数与事件绑定是瓶颈）。另一条同级路线是 deck.gl / MapLibre / Mapbox GL 直接消费 GeoJSON，适合大区域但要牺牲一些精细交互。〔S34 S41〕

2026-11 的判断：这条管线**只解决渲染，不解决可编辑与交付**，与《掩码到挤出》备忘里的 GLB + Draco 路线是互补关系（前者是 2D 交互图，后者是 3D 体量），不是替代关系。若同一份平面既要 2D 悬停图又要 3D 漫游，应当从真值层分别投影，而不是从 SVG 反推几何。〔S39〕

### 3.10 IFC 生态的 JSON 化工具链

§3.5 的结论是"IFC 是规范、JSON 是视图"，落到工具层有四条路（自 2026-11-12 调研并入并更新进度）：

| 路径 | 是什么 | 成熟度（2026-11） | 对我们的用法 |
|---|---|---|---|
| web-ifc（ThatOpen，xeokit 等广泛使用） | WASM 解析 IFC 为 JS 对象 + 三角网格，浏览器直读 | **事实标准** | 构件级 Web 查看首选 |
| xBIM Toolkit / XbimWebUI | .NET 解析 IFC，向 Web 输出模型与几何 | 成熟（.NET 栈） | 服务端校验与工程量 |
| ifcJSON（buildingsmart-community） | 社区用 JSON 序列化 IFC schema 的探索 | 实验性，非官方编码 | 只可参考，不宜作交付格式 |
| IFC5 / IFCX | buildingSMART 推进用语言无关的 **IFCX（JSON 化的模式语言）替代 Express** + JSON 友好序列化 | 截至 2024-12 仍在探索；**IFC4.x 仍是工作标准**（4.3 已落地，4.4 在前） | 长期观察，不进产品承诺 |

结论没变、理由更硬：**IFC 侧的 JSON 化是工具链在推，不是标准在推**。所以我们自己的 IFC 出口仍按《掩码到挤出》§10 的 P2 走 STEP/IfcWall 中线模型，Web 侧读取交给 web-ifc，而不是等 IFCX。〔S10 S35 S36 S37〕

### 3.11 Autodesk APS 与专有视图格式

APS（Autodesk Platform Services，原 Forge）用 **Model Derivative** 把 Revit/CAD/FBX 转成专有视图格式 SVF/SVF2，再由 **View & Data API** 以 JSON 暴露"场景图 / 模型树 / 属性"，可在 Web Viewer 里按楼层与构件浏览、做 2D minimap。〔S38〕

它**不是平面图 JSON 标准**，而是"厂商专有的、以 JSON 呈现的可视图数据"：几何来自设计源头，但只读为主、不可回写编辑，且绑定 Autodesk 账号与生态。与 §3.5 里的 ADX 分工是：APS 管**视图消费**，ADX 管**数据管道**。对我们的意义只有一条——如果客户是 Revit 深度用户且只要"网页里看模型 + 点构件查属性"，APS 是省事选项；一旦要我们自己的动线/展项/面积分析，就必须落到自有 schema。〔S14 S38〕

### 5.2 fishplan/v1 三层 schema 草案

内核三层（与《掩码到挤出》备忘第 3 节模式 A 同构，仅补齐标准侧要求的字段）：

```jsonc
{
  "$schema": "fishplan/v1",
  "meta": {
    "unit": "mm", "up": "z", "manhattan_default": true,
    "scale_anchor": {"required": true, "anchor_mm": 3600, "anchor_source": "业主提供客厅开间"},
    "copyright": "Vhuan Tech. Co., Ltd.", "locale": "zh-CN"
  },
  "geometry": {                                   // L1
    "walls":   [{"id":"W1","polyline":[[0,0],[3600,0]],"thickness_mm":200,"bearing":true,"orthogonal":true}],
    "slabs":   [{"id":"S1","polygon":[[...]],"z0":-120,"z1":0}],
    "rooms":   [{"id":"R1","polygon":[[...]],"room_type":"bedroom","finish":"wood"}]
  },
  "graph": {                                      // L2 —— 吸收 IndoorGML Dual Space 与 ResPlan 类型化边
    "nodes": ["R1","R2"],
    "edges": [{"from":"R1","to":"R2","portal":"D1","kind":"via_door"}]   // via_door|via_window|adjacency|direct
  },
  "openings": [                                   // L3 —— 洞口必须是构件，不是布尔结果
    {"id":"D1","host_wall":"W1","t_along_mm":1200,"width_mm":900,
     "sill_mm":0,"head_mm":2100,"kind":"door","operation":"swing","direction":"inward"}
  ],
  "properties": [                                 // 属性挂靠字典，不硬编码单位
    {"target":"R1","key":"net_area_m2","value":14.6,"definition":"bSDD:<uri> 或 GB55038:<clause>"}
  ],
  "projections": {"imdof":"./imdof.zip","dxf":"./plan.dxf","ifc4":"./plan.ifc"},
  "checks": {"watertight":true,"openings_in_host":true,"double_wall_merged":true}
}
```

五条设计理由：

1. `"$schema": "fishplan/v1"` 承担版本语义，转换与迁移按版本走（抄 Speckle type evolution 的思路）。〔S13〕
2. `geometry.walls.polyline` 是**中线**，`thickness_mm` 独立成字段——这是 DXF 分层、IFC `IfcWall`、工程量三方都能对齐的唯一写法。〔S10〕
3. `graph` 单独成层而非从几何反推，具身智能与导航消费方直接拿图，不必再跑一次布尔。〔S1 S4〕
4. `openings` 带 `host_wall + t_along_mm`，把"引用完整性"做成语法要求，与 SpatialLM/FMLM 的约束解码同源。〔S21 S22〕
5. `properties[].definition` 指向 bSDD 或 GB 条款，把"面积口径/单位/定义"从键名里解放出来。〔S9 S27〕

### 6.1 对 ExpoVR HallLayoutSpec 的启示

自 2026-11-12 调研并入，六条在本轮核实后依然成立，且可直接落到 `fishplan/v1`：〔S39〕

1. **借鉴 IMDF 的"楼层/单元/开口"分层词表**：HallLayoutSpec 已有 `zones` / `walls` / `doors` / `anchors`，可显式引入 `level`（带 ordinal）与 `connector` 语义，便于未来多馆多楼层与导览。注意用现行 1.9 的对象名，别沿用 Venue / Opening / Amenity 旧称。〔S6 S41〕
2. **借鉴 TopoJSON 的共享边界思想**：相邻分区目前各存一份矩形边界，改成共享边可消缝隙、减体积、利于渲染一致性——这也是《掩码到挤出》§7 坑 1"共壁重复"的正解。〔S34〕
3. **借鉴 IndoorGML 的双层空间（Dual Space）**：在 `circulation.path` 之外显式建"分区节点-连通图"，为寻路与观展动线优化打基础；这正是 `fishplan/v1` 的 `graph` 层。〔S4〕
4. **保留到 GeoJSON 的导出**：让平面能被 GIS 与 deck.gl 直接消费。〔S33〕
5. **面向 IFC 的映射**：墙/门/窗/空间对齐 `IfcWall` / `IfcDoor` / `IfcWindow` / `IfcSpace`，未来接设计源头或做构件级 3D 时有现成通道。〔S10〕
6. **继续用领域不变量校验（shapely）**：拓扑、面积、可达性三类断言是自定义 schema 相对通用标准的唯一护城河，`fishplan/v1` 的 `checks` 字段就是它的形式化。〔S39〕

两者关系一句话说清：**HallLayoutSpec 是 `fishplan/v1` 的展陈特化实例**（同一内核、不同业态预设），不应再维护第二套几何定义；米制、原点居中、矢量为准、位图永不作输入这四条既有约定保持不变。〔S39〕

2. **IndoorGML 2.0 的 JSON 编码不存在正式文本**：Part 2（GML/SQL/JSON）在核实时间点仍未定稿，因此本文档所有关于"IndoorGML 的 JSON"的表述，实际指的是社区实现 IndoorJSON，二者不可混为一谈。〔S4 S5〕
3. **IndoorJSON 的具体开源许可证未核到**，只确认其可实现与写入校验能力；若要在产品里直接复用其代码，必须先补许可核实。〔S5〕
4. **RESO 相关费用与采购周期（$2K–10K/月、2–4 月）来自第三方教学/科普页，不是 RESO 官方价目**，仅作量级参考；RESO 的正式口径是"字段命名与 Web API 规范"，不是数据质量标准，不要把它的会员费用与我们产品定价混用。〔S15〕
5. **GB 55038-2025 的具体数值未逐条核对规范原文**，取自地方政府与行业解读页面；落地引用前必须以标准正式文本为准。〔S27〕
6. **中房协团标草案不可得**，只知道征集公告与主编单位、时间节点，具体字段清单**不能提前当作已知**；第 5.2 节属性字典挂靠策略应视为"抢跑准备"而非"合规对齐"。〔S28〕
7. **xAIR 未能核实**：检索时被同名上市公司（NASDAQ 代码 XAIR，Beyond Air）与无关项目严重干扰，无法确认其平面表示细节与许可证，本文档不引用其任何结论。〔S30〕
8. **厂商自报数据一律隔离**：群核 5 亿场景 / 4.8 亿模型、Interior GS 1,000 场景 / 55.5 万实例、Kairos-HomeWorld 30 万套平面图、SPEAR 1.4 万接口、WalkerBench 161 城、SpatialLM 60 GB 显存——均为厂商公告、媒体转述或论文自报，**未经第三方复现**，不可作为我方能力对标或对外承诺的依据。〔S21 S24 S25 S30〕

## 附录 A 格式片段汇总

GeoJSON 的室内惯例（房间=面、门=点、走廊中线=线；楼层只能进 `properties`）〔S33〕：

```jsonc
{"type":"FeatureCollection","features":[
  {"type":"Feature",
   "properties":{"name":"客厅","category":"living","level":1,"area_m2":21.4},
   "geometry":{"type":"Polygon","coordinates":[[[0,0],[4.2,0],[4.2,5.1],[0,5.1],[0,0]]]}},
  {"type":"Feature","properties":{"name":"D1","category":"door"},
   "geometry":{"type":"Point","coordinates":[3.6,0.45]}}
]}
```

TopoJSON 的共享弧与量化（相邻房间共用同一段 `arcs` 索引，故无缝隙、体积小）〔S34〕：

```jsonc
{"type":"Topology",
 "transform":{"scale":[0.001,0.001],"translate":[0,0]},
 "arcs":[[[0,0],[4200,0]],[[4200,0],[4200,5100]],   // 右墙被两间房共用
          [[4200,5100],[0,5100]],[[0,5100],[0,0]],[[2100,0],[2100,5100]]],
 "objects":{"rooms":{"type":"GeometryCollection","geometries":[
   {"type":"Polygon","arcs":[[0,1,-4,4]],"properties":{"name":"客厅"}},
   {"type":"Polygon","arcs":[[-4,-2,2,-3]],"properties":{"name":"卧室"}}]}}}
```

ResPlan 的记录形态（dict → Shapely 几何，缺失类别写 EMPTY）〔S1〕：

```python
plan = {
    "bedroom":  MultiPolygon(...),   # 缺失时为 MULTIPOLYGON EMPTY，而不是删键
    "bathroom": Polygon(...),
    "wall":     MultiPolygon(...),   # 统一厚度的干净多边形，可直接挤出
    "door":     Polygon(...),
    "wall_depth": 0.21,              # 米；全库中位数约 21 cm
}
```

ResPlan 的类型化连通图（rooms 为节点）〔S1〕：

```jsonc
{"nodes": [{"id": 0, "room": "bedroom", "area_m2": 14.6}],
 "edges": [{"src": 0, "dst": 1, "kind": "via_door"},
           {"src": 1, "dst": 2, "kind": "adjacency"}]}
```

IMDF 的分层关系（GeoJSON feature 的属性侧）〔S6〕：

```jsonc
// unit.json —— 房间/单元；必须带 id，否则 level/unit 关联断裂
{"type":"Feature","properties":{"id":"U1","level_id":"L1","name":"客厅","category":"living"},
 "geometry":{"type":"Polygon","coordinates":[[[0,0],[3.6,0],[3.6,4.0],[0,4.0],[0,0]]]}}
```

CityJSON 的坐标量化（避免浮点膨胀）〔S8〕：

```jsonc
{"transform":{"scale":[0.001,0.001,0.001],"translate":[123.4,41.2,0.0]},
 "cityobjects":[{"id":"b1","type":"Building","geometry":[{"lod":"1.0","boundaries":[...]}],
                 "semantic":[{"attributes":{"address":"..."}}]}]}
```

SAREF4BLDG / NGSI-LD 的 BuildingSpace（JSON-LD）〔S12〕：

```jsonc
{"id":"urn:ngsi-ld:BuildingSpace:R1","type":"BuildingSpace","description":"客厅",
 "isDeccribedBy":{"type":"Relationship","object":"urn:ngsi-ld:Building:B1"},
 "observation":{"type":"Relationship","objects":["urn:ngsi-ld:Observation:temp1"]}}
```

MLS 侧的对照（**字段字典，不是几何**）：Centris `PropertyRooms` 只给长宽高等尺寸，`RoomDimensionsPolygonYN` 是布尔标记而非多边形〔S17〕；RESO Data Dictionary 2.1 定义"这个字段叫什么、什么类型"，不定义"这面墙在哪里"〔S15〕。

AI 侧的受约束输出（示意：引用完整性写进语法）〔S21 S22〕：

```text
wall w0 0 0 3600 0 200
wall w1 3600 0 3600 2800 200
room r0 bedroom [w0 w1 ...]
door d0 host w0 at 1200 width 900   # host 必须是已声明的 wall id
```
