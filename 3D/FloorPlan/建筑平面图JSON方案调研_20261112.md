## 〇、TL;DR 与选型速查

一句话：**"形状"归 GeoJSON/TopoJSON，"建筑语义"归 IMDF/IndoorGML/CityJSON，"构件级 BIM"归 IFC 生态，"Web 交互渲染"靠 D3/deck.gl/MapLibre 消费上述格式。** 没有任何一个现成标准是"为展厅平面而生的轻量矢量规格"——这恰恰是自定义 schema（如 HallLayoutSpec）存在的空间。

| 我要… | 首选 | 备选 |
|---|---|---|
| 纯几何 + 属性、工具链最广 | GeoJSON | TopoJSON |
| 共享边界、体积小、D3 渲染 | TopoJSON | GeoJSON+简化 |
| 商场/机场多楼层可导航、目录 | IMDF | IndoorGML |
| 室内寻路、空间连通图 | IndoorGML | IMDF+自建图 |
| 城市级/多建筑 3D 语义 | CityJSON | CityGML |
| 构件级 BIM（墙/门/窗/空间） | IFC(+web-ifc) | ifcJSON / IFC5 |
| 跨软件实时协同数据总线 | Speckle | IFC |
| 设计器手绘→可交互图 | SVG+D3 管线 | GeoJSON |

## 一、为什么用 JSON 表示平面图

传统平面图是位图（PNG/JPG）或 CAD 二进制（DWG/DXF），缺点是不可编程、不可交互、语义丢失。JSON 化的价值在于：几何与属性同构、天然适配 Web/JS 生态、可被 GIS/BIM/可视化库直接消费、易做增量传输与版本 diff、能把"非空间属性"（房间名、面积、展项、POI、状态）挂在几何上。核心矛盾是**几何表达 vs 语义/拓扑表达**——越靠语义/拓扑，越省空间、越利于导航与分析，但越需要约定词表。

## 二、方案全景（六大类）

1. 通用地理空间编码：GeoJSON、TopoJSON
2. 室内/建筑专用标准：IMDF、IndoorGML、CityGML/CityJSON
3. BIM / IFC 生态的 JSON 化：IFC4.x、ifcJSON、IFC5/IFCX、web-ifc、xBIM、xeokit
4. 平台/厂商专有：Autodesk APS（Model Derivative / View & Data）、Speckle
5. Web 可视化管线：SVG + D3.js（承接前文那篇教程）、deck.gl / MapLibre / Mapbox GL
6. 学术数据集 & 自定义 schema：CubiCasa5K、ResPlan、FloorPlanCAD，以及项目自定义（HallLayoutSpec）

## 三、逐方案详解

### 1. GeoJSON（RFC 7946）

IETF 发布的通用地理数据编码。基本单元：`geometry`（Point / LineString / Polygon / MultiPolygon / …）→ 包进 `Feature`（可带 `properties`）→ 汇成 `FeatureCollection`。用于室内时，惯例是"房间=Polygon、门=Point、走廊中线=LineString"，属性里放名称/类别/面积。

优点：开放、极稳定、几乎所有 GIS 与 Web 地图库都原生支持，是室内几何的"底座"。缺点：**没有内建的"楼层"概念，也没有建筑/室内词表**，楼层、房间类型、连通关系都得自己约定；对复杂建筑缺少拓扑（相邻房间会重复存边界）。

### 2. TopoJSON

GeoJSON 的扩展（并非官方标准，而是 D3 生态事实标准）。核心是**拓扑**：几何通过共享的"弧线 arcs"拼接，相邻多边形共用同一段边界，`objects` 引用 `arcs` 索引，配合 `transform`(scale/translate) 量化坐标。因此体积显著小于 GeoJSON，且天然保证相邻区域无缝、无重叠缝隙。

注意：这里的"弧"是 `[x,y]` 点序列，**不支持 SVG 弧/贝塞尔曲线**，曲线靠密集采样点近似。适合"区域多、共享边界多、要在浏览器里做悬停/寻路"的平面图（正是前文那篇教程的用法）。缺点：语义仍靠自定义属性；编辑/生成工具链不如 GeoJSON 普及。

### 3. IMDF（Indoor Mapping Data Format，Apple 主导 / OGC Community Standard）

由 Apple 与 Mapbox 等推动、被 OGC 收为社区标准。**本质是一组约定好词表的 GeoJSON FeatureCollection**，规定了建筑由哪些对象构成：`Venue`/`Building`、`Level`（带 ordinal 楼层序号，解决"上下叠放"）、`Unit`（房间/店铺/走道等空间）、`Opening`（门/通道）、`Amenity`/`POI`（设施与目的地），并配套 categories、place-types、styles 等分类表。

优点：跨建筑一致的结构，工具与导航引擎无需为每个场馆写特例；GeoJSON 生态可直接复用。缺点：**不是显式的图标准**——连通性靠 Opening 隐含，路径网络不是一等公民；不含实时定位。适合多场馆室内地图、数字导览目录。

### 4. IndoorGML（OGC 标准，GML/XML）

面向室内寻路的 OGC 标准。核心是 **DLS（Dual Level Space，双层空间）**：一层"胞元空间（cellular space）"表示房间/走廊/有界区域，一层"节点-关系图（node-relation graph）"——每个空间=节点、相邻空间连通=边。平面的意义落在"空间连通"而非仅形状上，天然适合路径计算（含跨层）。IndoorGML 2.0 进一步抽象了核心模型与空间/导航数据分层。

优点：导航图显式、寻路即插即用。缺点：是 GML/XML 而非 JSON，与 GeoJSON 管线不太合拍；模型偏重、上手门槛高。适合"寻路优先"的室内系统。

### 5. CityGML / CityJSON

CityGML 是 OGC 的城市级 3D 信息模型（含建筑、语义、多细节层次 LoD1–LoD4）。**CityJSON 是 CityGML 的紧凑 JSON 编码**：用 `vertices`（顶点表）+ 各 `objects`（含 `type`、`geometry`(以顶点索引构成的多面体)、`attributes`）表达，共享顶点、体积小、易被 JS/Python 读写；CityJSON 2.0 增加了几何实例化、纹理、地形等。

优点：语义丰富 + 3D + 城市尺度。缺点：偏宏观（建筑/城市），单栋建筑的室内房间级细节不是它的强项；室内需配合 IndoorGML/IFC。适合园区/城市级数字孪生。

### 6. IFC 生态（构件级 BIM 的 JSON 化）

IFC（Industry Foundation Classes，buildingSMART）是开放 BIM 交换标准，原生是 STEP 物理文件（Express 模式），构件级建模：`IfcWall`/`IfcDoor`/`IfcWindow`/`IfcSpace`/`IfcSlab`… 语义最完整。JSON 化路径有几种：

- **web-ifc（ThatOpen / 现 xeokit 等广泛使用）**：把 IFC 解析成 JS 对象与三角网格几何，浏览器端直接消费，是"IFC→Web"事实标准工具。
- **xBIM Toolkit / XbimWebUI**：.NET 解析 IFC，向 Web 输出模型与几何。
- **ifcJSON（buildingsmart-community）**：社区探索用 JSON 序列化 IFC schema 数据，便于 Web 交换。
- **IFC5 / IFCX（下一代 IFC）**：buildingSMART 正在推进的方向——用**语言无关的 schema（IFCX，一种 JSON 化的模式语言）替代 Express**，配合灵活的序列化（JSON 友好），让 BIM 数据脱离 STEP 文本、更适配 Web/流式。截至 2024 年底仍在探索阶段，**IFC4.x 仍是当前工作标准**（4.3 已落地，4.4 在前）。

优点：构件级语义、行业通用、可追溯到设计源头。缺点：模型庞大、复杂、对"轻量平面展示"是杀鸡用牛刀；纯 JSON 直读生态尚未完全成熟（多靠 web-ifc 这类解析器）。

### 7. Speckle（开源 AEC 数据平台/总线）

面向建筑/工程/施工的开源数据中枢，自定义的 **JSON 对象模型**：每个对象有 `id`(内容哈希)、`speckle_type`(类型，如 `Base`/`Geometry.Mesh`/`Building.Room` 或应用自定义类型)、`applicationId`(来自 Revit/Rhino 等的原始 ID)、以及属性与嵌套几何基元（Point/Line/Polycurve/Mesh 等），支持分层与"detached"分块存储。多连接器（Revit/Rhino/Grasshopper/Blender/Unity…）互通。

优点：跨软件实时同步、版本化、可编程、比 IFC 轻。缺点：是平台化方案（需服务器/工作区），不是"打开即用"的平面图文件标准。适合多专业协同与把 BIM 数据喂给可视化/游戏引擎。

### 8. Autodesk Platform Services（APS，原 Forge）

Autodesk 云 API。**Model Derivative** 把 Revit/CAD/FBX 等转成专有视图格式 SVF/SVF2，通过 **View & Data API** 以 JSON 暴露"场景图/模型树/属性"，可在 Web Viewer 里按楼层/构件浏览、做 2D minimap。它不是"平面图 JSON 标准"，而是**厂商专有的、以 JSON 呈现可视图数据**的工程方案。优点：设计源头直连、企业级；缺点：绑定 Autodesk 生态、非开放格式。

### 9. SVG + D3.js 管线（承接前文教程）

设计器（Inkscape）手绘 SVG → 取路径 `d`（绝对坐标）→ SVGOMG 压缩 / SvgPathEditor 整形 → path→polygon → 组装 **TopoJSON**（`type/objects/arcs`）→ `topojson.feature()` 转 GeoJSON → `d3.geoPath` 生成 SVG 路径 → CSS `:hover` 交互。优点：完全可控、前端友好、适合展厅这类"区域+悬停"的交互平面图。缺点：前期数据录入重、SVG 规模变大时性能吃紧。

### 10. 学术数据集 / 专用矢量格式

- **CubiCasa5K**：5000 张住宅平面图，含标注（墙/门/窗/房间），既有栅格也有**结构化 JSON 标注**，广泛用于平面图识别/生成研究。
- **ResPlan（2025）**：17000+ 住宅平面图的**大规模矢量-图（vector-graph）数据集**，以结构化矢量元素表示，面向平面图理解与生成。
- **FloorPlanCAD / RPLAN** 等：CAD 矢量或参数化平面数据集。

这些偏"研究/算法训练"用途，几何多为元素级（线段/弧/多边形 + 语义标签），可借鉴其"元素 + 语义标签 + 图结构"的组织方式。

### 11. 自定义 schema（如 ExpoVR HallLayoutSpec）

当需求是"轻量、面向特定业务（展厅）、单一数据源同时驱动 渲染/DXF/3D"时，业界通行做法是**自建 JSON schema**：定义场地轮廓、分区、墙/门/窗、展项锚点、动线、约束等，并写校验器（如用 shapely 强制拓扑/面积/可达性不变量）。HallLayoutSpec 就属此类——米制、原点居中、矢量为准、位图永不作输入。优点：贴合业务、可加领域不变量；缺点：需自证与标准（GeoJSON/IFC）的互转能力。

## 四、横向对比表

| 方案 | 几何 | 拓扑/共享边 | 楼层 | 语义/词表 | 3D | 载体 | 生态/工具链 | 典型场景 |
|---|---|---|---|---|---|---|---|---|
| GeoJSON | 点/线/面 | 无 | 无(靠属性) | 无固定 | 否 | JSON | 极广 | 通用几何底座 |
| TopoJSON | 弧线共享 | 强 | 无 | 自定义 | 否 | JSON | D3 生态 | 区域悬停/寻路前端 |
| IMDF | GeoJSON 面 | 靠 Opening | Level 有序 | 建筑词表 | 否 | GeoJSON 集 | Apple/OGC、导览 | 多场馆室内地图 |
| IndoorGML | 胞元空间 | 节点-关系图 | 有 | 强(导航) | 部分 | GML/XML | OGC、学术 | 室内寻路优先 |
| CityJSON | 顶点+多面体 | 共享顶点 | 弱 | 城市语义 | 是(LoD) | JSON | 3D 城市 | 园区/城市孪生 |
| IFC(+web-ifc) | B-rep/构件 | 构件级 | Storey | 极强 | 是 | STEP→JS | BIM 行业 | 构件级设计/交付 |

## 五、按需求选型建议

纯展示 + 悬停交互、前端可控：TopoJSON + D3（或 GeoJSON + deck.gl/MapLibre）。多楼层、需导览且要跨场馆一致：IMDF。寻路是核心：IndoorGML（或 IMDF + 自建连通图）。要连设计源头、构件级：IFC + web-ifc（长期关注 IFC5/IFCX）。多专业实时协同：Speckle。城市/园区级：CityJSON。业务高度定制且要"一份 JSON 驱动渲染/DXF/3D + 领域校验"：自定义 schema，并保留到 GeoJSON/IFC 的导出通道。

## 六、对 ExpoVR HallLayoutSpec 的启示

第一，**借鉴 IMDF 的"楼层/单元/开口"分层词表**：HallLayoutSpec 已有 zones/walls/doors/anchors，可显式引入 `Level`（ordinal）与 `Opening` 语义，便于未来多馆多楼层与导览。第二，**借鉴 TopoJSON 的共享边界思想**：相邻分区目前各自存矩形边界，若走"弧共享"可消除缝隙、减小体积、利于渲染一致性。第三，**借鉴 IndoorGML 的双层空间**：把 `circulation.path` 之外，显式建"分区节点-连通图"，为寻路/观展动线优化打基础。第四，**保留到 GeoJSON 的导出**：让平面图能被 GIS/deck.gl 直接消费。第五，**面向 IFC 的映射**：墙/门/窗/空间可对齐 `IfcWall/IfcDoor/IfcWindow/IfcSpace`，未来若接设计源头或做构件级 3D，有现成通道。第六，**继续用领域不变量校验**（shapely）——这是自定义 schema 相对通用标准的护城河。
